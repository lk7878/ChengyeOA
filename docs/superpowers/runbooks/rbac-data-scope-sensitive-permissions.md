# RBAC、数据范围与敏感权限操作手册

本手册适用于 SPEC-004 已实施的权限中心。它覆盖角色、数据范围、字段能力、临时授权、权限追踪、L4 查看、迁移与故障处置。SPEC-005 的系统管理员审核、配置发布和高风险复核尚未实施，不得用本手册绕过后续审核设计。

## 1. 安全边界

- 权限判定以服务端实时数据库状态为准，JWT 只证明身份和凭据版本。
- 一项授权必须同时满足动作权限、数据范围、有效期和账号/角色状态；多个有效授权按记录集合并集计算。
- 业务角色不得获得权限治理写权限、保留系统角色或未接入的特殊权限。
- `SYSTEM_SUPER_ADMIN` 是信任根，不绕过字段投影、L4 用途、审计、事务和乐观锁。
- 角色、授权、汇报关系和审计记录只保留历史，不通过业务接口物理删除。
- 不在工单、日志或截图中记录令牌、密码、身份证原文、手机号原文或案件材料。

## 2. 角色设计

1. 先按稳定岗位职责设计角色，不按具体人员建角色。例如“重庆分所负责人”“跨分所医疗团队成员”。
2. 角色代码创建后不可修改，使用大写字母、数字和下划线表达稳定语义。
3. 只勾选完成岗位工作的最小动作权限；菜单权限仅控制入口，不替代服务端动作权限。
4. 为每个受范围约束的资源绑定数据范围。只有动作、没有资源范围时，不产生可访问记录。
5. 单独配置字段读取等级、写入和导出能力。字段 `NONE` 是硬拒绝，不能被其他角色放宽。
6. 停用前先撤销或结束有效授权。已使用角色不物理删除。

## 3. 数据范围选择

| 类型 | 适用场景 | 操作注意事项 |
| --- | --- | --- |
| `ALL` | 全所治理 | 仅授予确需全所数据的角色 |
| `HQ_SCOPE` | 总所及总所部门 | 不包含地区分所业务数据 |
| `ORG` | 指定组织 | 按需决定是否包含下级组织 |
| `BRANCH` | 指定地区分所 | 适合分所负责人和分所职能人员 |
| `TEAM` | 跨分所专业团队 | 只包含生效团队关系和团队归属记录 |
| `SELF` | 本人 | 账号必须绑定员工档案 |
| `SELF_AND_SUBORDINATES` | 本人及汇报下属 | 依赖生效汇报关系，不按岗位名称推断 |
| `CUSTOM` | 明确目标集合 | 当前保留服务端能力，管理端目标编辑器未开放 |

创建可复用范围时，必须选择系统支持的标准类型和有效组织/团队。多个角色或专项授权的范围取并集；结束的任职、团队成员和汇报关系不会被重新纳入。

## 4. 字段分级

- `L1`：普通业务字段，按资源读取权限返回。
- `L2`：需要基础保护的字段，按策略返回或脱敏。
- `L3`：敏感字段，默认脱敏或省略；查看原文需要明确字段能力并写访问审计。
- `L4`：高敏感字段，例如身份证号；必须具备专项动作权限、命中数据范围、填写至少 10 个字符的具体用途，并在同一事务中成功写审计后才返回原文。
- `FORBIDDEN`：密码、令牌和安全内部字段，任何业务投影都不返回。

L4 原始值只在当前查看抽屉中临时保存。关闭抽屉后会清除，不进入 Zustand、localStorage、URL 或权限追踪结果。

## 5. 用户授权

### 永久角色

用于稳定岗位。选择用户和业务角色，确认生效时间后授权。系统保留授权人、来源、生效时间和历史状态。

### 临时角色

必须填写开始、结束时间和具体原因，最长 90 天。到期后实时失效，无需后台任务。到期记录仍显示为历史，可再执行撤销形成明确闭环。

### 临时专项权限

只允许目录中已注册并开放的 `SPECIAL` 权限，必须绑定数据范围、原因和有效期，最长 30 天。SPEC-004 只允许超级管理员操作；后续审核由 SPEC-005 承接。

### 撤销

撤销前核对用户、角色/权限、有效期和影响范围，填写撤销原因并提交当前版本。撤销立即生效但不删除历史。发生 `VERSION_CONFLICT` 时刷新最新状态，不自动重放旧请求。

## 6. 权限追踪

- “我的权限”只解释当前用户自己的有效权限。
- “权限追踪”供治理人员选择用户和权限代码，查看允许/拒绝、来源角色、有效期、数据范围类型和字段能力。
- 追踪结果不返回业务记录、范围目标全集、SQL 谓词或敏感字段原值。
- 排障顺序：账号状态、角色状态、授权有效期、动作权限、资源范围、字段能力、专项权限、目标记录是否命中。

## 7. 汇报关系

`SELF_AND_SUBORDINATES` 依赖正式汇报关系。新增或替换经理时必须使用当前版本；系统拒绝本人管理、直接循环和间接循环。结束关系保留历史。员工离职前必须先处理其当前下属，避免产生无负责人链路。

## 8. 迁移与备份

1. 确认发布版本、维护窗口、备份责任人和回滚责任人。
2. 按 `postgresql-backup-restore.md` 完成备份并验证恢复能力。
3. 使用外部环境配置加载 `DATABASE_URL`、`JWT_SECRET` 和 `APP_KEYS`，不得输出其值。
4. 在 `LayerManage/law-firm-system` 执行：

```powershell
npx.cmd -y -p node@22.14.0 -p npm@10.9.2 npm.cmd run db:deploy
```

5. 验证 32 张应用表、61 条权限目录、初始化根组织、首位超级管理员和 `SYSTEM_SUPER_ADMIN` 关系。
6. 抽查历史业务角色和用户角色仍存在，未知旧权限被停用而非删除。
7. 启动应用后验证当前用户摘要、角色列表、范围列表、权限追踪和一条受范围限制的员工读取。

本地迁移验收可执行：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File apps/server/scripts/db/rehearse-spec-004-migration.ps1
```

它只允许固定数据库 `chengye_oa_spec004_migration_test`，并在 `finally` 删除。不得改名后用于生产。

## 9. 信任根检查

高影响操作后确认：

- `SystemInitialization.PRIMARY` 仍指向同一根组织和首位超级管理员；
- 首位超级管理员用户和 `SYSTEM_SUPER_ADMIN` 角色均启用且关系有效；
- 没有第二个保留系统角色，也没有通过普通授权接口授予该角色；
- 权限目录代码唯一，系统目录之外的旧权限保持禁用；
- 审计只包含稳定标识、动作、状态、版本和时间，不包含敏感原值。

## 10. 到期与事件处置

授权到期由请求时实时判定。若出现“到期后仍可访问”，立即停止相关写操作并检查服务器时间、授权有效期、账号/角色状态和是否存在其他并集授权。

怀疑越权、L4 泄露、审计失败或信任根异常时：

1. 停止相关账号或角色的业务写入，保留脱敏证据。
2. 撤销可疑临时授权，不删除历史记录。
3. 获取数据库法证备份，核对授权追踪和操作日志。
4. 检查是否存在其他角色/团队/汇报范围形成并集访问。
5. 制定经复核的修复方案后恢复服务。

不要使用数据库重置、手工删行、直接修改版本、伪造审计或重建信任根作为恢复捷径。
