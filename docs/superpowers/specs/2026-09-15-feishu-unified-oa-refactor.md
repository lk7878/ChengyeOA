# SPEC-UNIFIED-OA-20260915：飞书式全站统一设计与原 OA 重构

状态：用户已授权产品方向与重构范围；U0/U1 导航契约及全站路由矩阵已补齐，U2 统一框架已实现，U3 已完成本批框架验收。U4–U7 业务深度整合仍待执行，不以 approved 标记或框架接入替代全站验收。

## 1. 用户授权与目标

用户在 2026-09-15 侧会话明确要求：原 OA 的功能设计全部统一到参考飞书的最新设计；出现冲突时，以参考飞书的新设计为主；允许大范围推翻和重构原 OA，尤其是 UI 左侧功能区布局；尽量不大范围修改知识库和智慧办案架构。

承接此前确认：所有用户共用一种界面，根据权限展示资源与操作；任何修改从 spec 开始。侧会话将新增需求落盘后交回原主会话实施，不另开一条并行代码重构线。

目标是统一产品结构、导航、业务操作及协作能力。云盘和多维表格成为全站工作方式的基础，旧功能融入该体系，不能仅在旧侧栏增加“云盘”后继续长期维持两套交互。

“参考飞书”沿用 [SPEC-DRIVE-20260915](2026-09-15-feishu-cloud-drive-resource-center.md) 与 [SPEC-COLLAB-20260914](2026-09-14-feishu-aligned-collaborative-workspace.md) 的公开依据和自建边界，不表示接入飞书托管后端或复制其私有源码。

## 2. 优先级与替代边界

| 情形 | 本次规则 |
|---|---|
| 旧菜单、路由组织、布局、表单/列表模式与新协作方式冲突 | 新统一设计优先，允许合并、替换、移除旧入口及重写页面 |
| 旧组件、服务拆分和数据模型妨碍新设计 | 可重构，不强制永久保留旧实现；先明确新契约、迁移及兼容方案 |
| 同一业务对象有传统页面和多维表格入口 | 使用同一权威数据与业务规则，不能复制成两套事实 |
| 原始数据、身份授权、业务状态及审计 | 重构不能静默丢失数据、扩大权限或跳过业务校验；业务语义调整先修订对应规格 |
| 知识库、智慧办案 | 优先保留架构；仅做统一入口、外层视觉、身份衔接和必要适配 |
| 旧验收和实施记录 | 保留历史事实，新增替代条款；旧页面通过不代表新设计验收通过 |

本规格向前替代“云盘与原模块并列即可完成整合”的过渡性设计，不废弃已经实现的云盘权限、移动、回收、快捷方式与最近访问。广泛重构授权不包含删除真实数据、重置数据库、推送或生产部署。

## 3. 全站信息架构与左侧功能区

### 3.1 导航基线

```text
全局顶栏：组织 / 当前位置 / 搜索与账号    知识库 / 智慧办案
全局左侧：工作台、云盘、业务应用、数据分析、管理中心
当前区域：按上下文显示目录或应用内导航
  云盘：个人/共享文件夹、最近访问、资源列表
  多维应用：数据表目录、视图、网格和详情
  业务应用：业务资源入口、视图、受控办理页面
  管理中心：组织、岗位、人员、身份授权和系统治理
```

以上为本次 OA 的信息架构基线，不宣称飞书官方具有完全相同的菜单；主会话在实施前补齐每个实际路由的去向与示意。

1. 旧侧栏的线索、客户、合同、案件、财务、库存、绩效、组织、权限等，不再全部作为全局同级菜单常驻展开。按使用场景进入业务应用或管理中心，并保留授权范围内的快捷到达。
2. 全局导航与上下文目录层级明确，不同时堆叠旧 OA 完整侧栏、云盘树和表目录三套宽侧栏。进入应用后保持全局定位和返回路径。
3. 工作台承接待办、通知和常用入口；云盘承接资源组织；业务应用承接业务任务；数据分析承接统一指标；管理中心承接配置治理。
4. 所有角色复用同一框架与组件；按有效权限筛选内容。管理员不另用一套日常业务 UI，员工也不通过隐藏菜单获得数据隔离。
5. 列表、字段配置、视图、筛选、排序、分组、记录详情、保存与失败反馈采用共同交互规则。专门的审批、核算等流程可保留适合该任务的页面。
6. 左侧收展、窄屏抽屉、键盘导航、面包屑和返回定位纳入实现。沿用现有 1440/1024/390 宽度检查，不能以截图占位替代真实路由和动作。
7. 知识库和智慧办案优先保留相邻的全局顶栏入口，不因全站重构将其内部界面强行改为表格或文件夹。

## 4. 原模块整合范围

| 模块范围 | 目标归属及统一方式 | 必须保留或显式迁移的能力 |
|---|---|---|
| 线索、公海、到访、跟进 | 业务应用中的协作表、日历及办理入口；以现有线索/跟进适配作为首批验证 | 领取/分配、状态流转、跟进历史、敏感字段和数据范围 |
| 客户、渠道、谈案、合同 | 统一资源入口、视图、详情与关联，按批次连接正式业务数据 | 客户唯一性、合同关联、生效流程及原业务 ID |
| 案件业务管理 | 统一业务表和交付工作台；区别于智慧办案引擎 | 节点、材料、案件权限、交付及归档规则 |
| 财务、发票、退款、成本 | 统一框架、数据视图和受控动作 | 金额口径、核算、审批、关联及审计 |
| 库存、领用、盘点 | 统一应用内目录和表格能力 | 出入库一致性、库存约束和操作记录 |
| 绩效、仪表盘、统计、异常数据 | 数据分析或相应业务应用，统一指标来源 | 指标定义、授权过滤和追溯 |
| 审批、通知、待办 | 工作台与业务记录联动，集中管理个人待处理任务 | 状态机、处理授权、幂等和历史记录 |
| 用户、员工、组织、岗位、团队、角色与权限 | 管理中心共用身份及授权基础，区分账号/员工/资源协作者职责 | 账号员工映射、岗位生效、继承限制及撤权 |
| 知识库、智慧办案 | 统一入口与必要适配，保留独立内部架构 | 云端 Wiki 与本地 Harness 的数据、权限及运行边界 |

主会话必须按实际路由核对本表，将遗漏模块补入迁移矩阵；不能只做线索示范后宣告全站重构完成。

## 5. 业务数据与权限统一

1. 建表区分“自定义协作表”和“连接业务数据”。正式线索、客户、合同等通过稳定 ID 连接权威数据，不以手工复制创建影子业务系统。
2. 自定义表可服务灵活场景；名称相似不自动与核心业务合并，也不自动赋予财务或审批效力。正式字段与扩展字段的来源、可编辑性清楚可见。
3. 正式记录从云盘、业务应用、通知或旧直链打开时，读取同一对象；因额外资源限制产生的可见范围差异可以存在，但不得扩大原业务权限，且应解释有效权限来源。
4. 签约、收款确认、库存变更等经受控业务动作执行，不以普通单元格任意赋值替代。允许重构业务服务实现，但保留经过规格定义的校验和审计语义。
5. 普通用户默认只看自己填写的记录，负责人查看授权范围全部数据。既有业务主体、创建人/负责人等规则在迁移矩阵中明确，不能混用身份字段或静默改写既有数据范围。
6. 组织身份、岗位授权、资源共享、行/列权限和业务动作权限共用可追溯体系。云盘和旧模块不得各维护一份员工或角色。
7. 迁移必须考虑旧书签、通知链接、附件关联、视图偏好和审计引用。旧页面可移除，必要的旧 URL 通过受控跳转/解析继续定位原记录；无权访问时明确拒绝。

## 6. 知识库与智慧办案保护边界

沿用 [统一桌面与本地 Harness 规格](2026-09-13-unified-desktop-local-harness.md) 的最新契约，而非被其替代的历史浏览器方案。

- 知识库继续由云端管理员维护，普通律师及本地 Harness 只读检索；不将普通云盘文件夹共享规则直接替代 Wiki 的写入和编译权限。
- 智慧办案继续运行本地 Harness，保留原生工作区、会话、模型、工具授权和插件机制；不重写为云端聊天页或通用多维表。
- 不自动同步个人材料、会话或本地目录到云盘/OA/Wiki；主动成果提交沿用既有规则。
- 允许外层布局、按钮样式、入口定位和必要鉴权衔接调整；切换 OA 模块不得重建或丢失已有办案会话。
- 默认不改动 Wiki 存储/索引/编译链路或 Harness 核心架构。确有跨边界依赖时，先记录必要性、影响和最小适配设计；主会话优先选择局部适配，不把全站统一理解为必须重写这两部分。
