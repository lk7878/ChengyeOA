# SPEC-002：首次系统初始化与超级管理员信任根设计

> 状态：已批准，待实施
> 日期：2026-07-15
> 批准日期：2026-07-15
> 需求基线：`律所闭环管理系统需求开发文档.md` V1.0
> 前置基线：`docs/superpowers/specs/2026-07-12-engineering-baseline-postgresql-migration-design.md`
> 关联设计：`docs/专项设计/角色权限与数据范围设计.md`、`docs/专项设计/系统管理员与超级管理员权限设计.md`
> 实施约束：本 Spec 审核通过后必须单独生成实施 Plan；本轮不生成业务代码。

## 1. 背景

SPEC-001 已建立 PostgreSQL 16 空数据库基线，并明确禁止通过 seed、应用启动或 migration 隐式创建组织、账号和经营数据。系统目前因此没有可登录的受信任管理身份，也没有能够证明“本系统已经完成首次初始化”的永久状态。

首位超级管理员是后续组织架构、人员主数据、权限体系和管理员治理的信任根。如果直接恢复演示 seed、提供公开初始化接口或把超级管理员伪装成员工，将产生默认凭据泄露、重复初始化、组织数据污染和权限边界模糊等风险。

本 Spec 只解决一个问题：在已完成 migration 的空 PostgreSQL 数据库中，通过一次性、可审计、可并发保护的离线命令，建立根律所、首位系统超级管理员和永久初始化状态，并提供受控的离线账号恢复能力。

## 2. 目标

1. 通过一次性交互式 CLI 创建根律所、系统超级管理员角色、首位超级管理员账号和永久初始化记录。
2. 初始化必须具备原子性、并发互斥、失败回滚、重复执行拒绝和安全审计能力。
3. 首位超级管理员使用初始密码登录后必须先修改密码，完成前不得访问 OA 业务功能。
4. 密码修改或离线恢复后，既有访问令牌和刷新令牌必须立即失效。
5. 在没有第二位超级管理员的阶段，提供环境开关、人工确认和审计保护下的离线恢复命令。
6. 保持超级管理员账号与员工档案解耦，为后续组织与人员 Spec 预留正式绑定能力。
7. 不恢复 seed，不提供 Web 初始化向导，不在启动、安装或 migration 中隐式写入业务数据。

## 3. 非目标

本 Spec 不包含：

1. 总所下属部门、地区分所、岗位、员工档案和完整组织树。
2. 超级管理员账号与真实员工档案的绑定。
3. 第二位超级管理员、系统管理员账号管理及管理员操作复核。
4. 完整 RBAC、数据范围、字段权限、特殊权限和权限配置页面。
5. MFA、SSO、短信、邮件或自助找回密码。
6. 客户、线索、合同、案件、财务、人事等业务数据初始化。
7. 演示账号、默认密码、公开初始化 API 或 Web 初始化向导。
8. 对 LawLink、LexNebulis 或历史 SQLite 数据的导入。

上述能力分别由后续 Spec 承接：

- SPEC-003：组织架构与人员主数据。
- SPEC-004：RBAC、数据范围与敏感权限。
- SPEC-005：系统管理员治理、操作审核与数据干预。
- 身份认证安全专项 Spec：MFA、SSO、设备与会话安全增强。

## 4. 方案决策

### 4.1 采用方案：领域服务 + 薄 CLI

初始化规则由 `SystemBootstrapService` 承担，CLI 只负责环境加载、交互输入、确认提示、调用服务和映射退出码。离线恢复由独立的 `SuperAdminRecoveryService` 和恢复 CLI 承担，不与首次初始化混合。

采用该方案的原因：

1. 关键事务和业务规则能够脱离终端进行单元测试与 PostgreSQL 集成测试。
2. CLI 不持有数据库业务规则，避免后续维护形成第二套实现。
3. 首次初始化与紧急恢复的授权条件不同，分离后更容易审计和限制。
4. 后续如果增加受控运维入口，可复用领域服务，但不得绕过本 Spec 的安全前置条件。

### 4.2 不采用的方案

| 方案 | 不采用原因 |
| --- | --- |
| Web 首次设置向导 | 增加公开攻击面，难以证明初始化入口已永久关闭 |
| 应用启动时自动创建 | 隐式写入数据，违反 SPEC-001 空库和可重复启动约束 |
| Prisma seed 创建管理员 | 容易混入默认凭据，且 seed 不能承担永久初始化状态与离线恢复治理 |
| 仅在 CLI 中直接写 Prisma | 规则、交互和事务耦合，难以测试和复用 |

## 5. 系统边界与组件

### 5.1 `SystemBootstrapService`

职责：

1. 获取 PostgreSQL 事务级初始化锁。
2. 校验数据库是否满足“已迁移、未初始化、无业务数据”的条件。
3. 校验根律所名称、超级管理员用户名和初始密码。
4. 在单一数据库事务中创建根组织、超级管理员角色、账号、角色关系、初始化记录和审计记录。
5. 对重复初始化、状态冲突和并发竞争执行失败关闭。

该服务不得读取终端、打印日志、解析命令行参数或签发登录令牌。

### 5.2 `bootstrap-system` CLI

对外命令固定为 `npm run system:bootstrap`。职责：

1. 加载并校验现有后端环境配置。
2. 验证当前为交互式终端。
3. 显示脱敏后的数据库主机、端口和数据库名。
4. 隐藏输入密码和确认密码。
5. 要求输入确认短语 `INITIALIZE <dbName>`。
6. 调用 `SystemBootstrapService` 并输出不含敏感信息的结果。

### 5.3 `SuperAdminRecoveryService`

职责：

1. 验证系统已初始化并定位 `SystemInitialization.superAdminUserId` 指向的首位超级管理员。
2. 校验恢复环境开关、目标账号、恢复原因和新临时密码。
3. 在单一事务中更新密码、强制改密状态、凭证版本和锁定状态，并写入审计记录。
4. 不得创建账号、变更角色、绑定员工、替换初始化记录或恢复任意其他用户。

### 5.4 `recover-super-admin` CLI

对外命令固定为 `npm run super-admin:recover`。恢复只在环境变量 `ALLOW_SUPER_ADMIN_RECOVERY=true` 时开放；其他值，包括缺失、空值、`1` 和大小写变体，均视为关闭。

CLI 必须交互输入目标用户名、新临时密码、确认密码和恢复原因，并要求输入确认短语：

```text
RECOVER <dbName> <username>
```

### 5.5 Web 与 HTTP 边界

1. 不提供任何初始化、重新初始化或离线恢复 HTTP 接口。
2. Web 仅新增强制改密页面和对应路由保护。
3. `POST /api/v1/auth/login` 继续作为唯一登录入口。
4. 新增强制改密接口 `POST /api/v1/auth/password/forced-change`。
5. 改密完成前只允许访问登录、强制改密、退出和健康检查能力；其他 API 一律拒绝。

## 6. 数据模型

### 6.1 `SystemInitialization`

新增单例模型，使用固定主键 `PRIMARY`：

| 字段 | 约束 | 说明 |
| --- | --- | --- |
| `id` | 固定值 `PRIMARY`，主键 | 保证全系统只有一个初始化状态 |
| `version` | 整数，初始值 `1` | 标识初始化契约版本，不是数据库 migration 版本 |
| `rootOrganizationId` | 必填 | 初始化创建的根律所 ID |
| `superAdminUserId` | 必填 | 首位超级管理员用户 ID |
| `completedAt` | 必填，UTC | 初始化事务完成时间 |

只要该记录存在，系统即永久视为已初始化。应用不得提供删除、重置、覆盖或修改该记录的接口。数据库备份恢复必须保留此记录。

### 6.2 `Organization`

初始化只创建一条根组织：

- `type = FIRM`
- `parentId = null`
- `status = ENABLED`
- 名称由 CLI 输入，去除首尾空白后长度为 2 至 100 个字符。

本 Spec 不创建分所、部门、岗位或员工。

### 6.3 `Role`

在现有 `Role` 中新增全局唯一且应用层不可修改的 `code` 字段。首位超级管理员角色固定为：

- `code = SYSTEM_SUPER_ADMIN`
- `name = 系统超级管理员`
- `type = SYSTEM`
- `status = ENABLED`

本 Spec 不创建 `Permission` 或 `RolePermission` 记录。角色代码只建立可信身份；完整授权决策由 SPEC-004 实现，不得把该角色解释为可绕过数据库、审计或应用安全边界。

### 6.4 `User`

在现有模型中新增：

| 字段 | 初始值 | 作用 |
| --- | --- | --- |
| `mustChangePassword` | `true` | 首次登录必须修改密码 |
| `credentialVersion` | `1` | 令牌与当前凭据版本绑定 |
| `passwordChangedAt` | `null` | 最近一次密码变更时间；初始化临时密码不计入正式变更 |
| `failedLoginCount` | `0` | 连续失败次数 |
| `lockedUntil` | `null` | 临时锁定截止时间 |

首位超级管理员：

- `status = ENABLED`
- `employeeId = null`
- 通过 `UserRole` 关联 `SYSTEM_SUPER_ADMIN`

不得创建虚假 `Position` 或 `Employee`。后续 SPEC-003 可将该用户绑定到真实员工，但不得因此更换用户主键或丢失审计链。

### 6.5 `LoginLog`

为支持成功、失败、未知账号和锁定事件，将登录日志调整为安全事件记录：

- `userId` 可空，用户删除时保留日志并置空关联。
- 保存规范化后的 `usernameSnapshot`。
- 增加 `outcome`：`SUCCESS`、`FAILURE`、`LOCKED`。
- 增加稳定的内部 `reasonCode`，不得保存原始异常或密码。
- 保留 IP、User-Agent 和 UTC 时间。

登录日志和操作日志均不得通过普通业务或管理 API 修改、删除。

## 7. 初始化前置条件

CLI 调用领域服务前后必须共同保证：

1. `DATABASE_URL` 为 PostgreSQL URL，并通过现有环境校验。
2. 数据库可连接，且所有已提交 Prisma migrations 已成功应用；存在待应用、失败或漂移状态时拒绝初始化。
3. `_prisma_migrations` 以外的全部应用表均无业务记录。
4. `SystemInitialization` 中不存在 `PRIMARY` 记录。
5. 不存在任何组织、用户、角色、用户角色或操作日志记录。
6. 不自动清理、不采纳、不覆盖任何冲突数据。

如果初始化记录不存在，但任意应用表已有数据，统一判定为“不一致状态”。系统必须失败关闭，提示人工调查，不得猜测已有数据来源，也不得提供 `--force` 参数。

## 8. 初始化数据流

1. 操作人员运行 `npm run system:bootstrap`。
2. CLI 校验环境和交互式终端，输出脱敏数据库目标。
3. CLI 依次读取根律所名称、超级管理员用户名、初始密码和密码确认。
4. 用户名去除首尾空白并转为小写；只允许 3 至 64 位 ASCII 字母、数字、点、下划线和连字符。
5. CLI 要求输入 `INITIALIZE <dbName>`；不完全匹配时结束且不写数据。
6. 服务开启数据库事务，并获取固定键的 PostgreSQL 事务级 advisory lock。
7. 服务在锁内重新执行初始化状态和空库校验，避免检查与写入之间发生竞争。
8. 服务依次创建根组织、系统超级管理员角色、用户、用户角色、初始化状态和 `SYSTEM_BOOTSTRAP` 审计记录。
9. 任一步失败，包括审计失败，整个事务回滚。
10. 提交成功后 CLI 只输出创建成功、根组织名称、管理员用户名和后续登录提示，不输出密码、Hash、令牌、完整连接串或内部主键。

两个进程并发执行时，只允许一个事务成功。后获得锁的事务必须看到初始化记录并以“已经初始化”退出，不得等待后再次写入。

## 9. 登录与强制改密

### 9.1 登录结果

当用户名和密码正确且 `mustChangePassword = true` 时，登录接口只返回：

```json
{
  "mode": "PASSWORD_CHANGE_REQUIRED",
  "passwordChangeToken": "<redacted>",
  "expiresIn": 300
}
```

不得同时返回普通访问令牌、刷新令牌、用户权限或业务数据。

普通登录成功时保持现有认证响应语义，但签发的访问令牌和刷新令牌必须增加令牌类型与凭证版本声明。

### 9.2 改密令牌

- `tokenType = password_change`
- 有效期固定为 5 分钟
- 包含 `userId` 和签发时的 `credentialVersion`
- 只能调用强制改密和退出接口
- 不可用于刷新、访问 `/auth/me` 或任何业务接口
- 过期、用户禁用、账号锁定或凭证版本不一致时立即拒绝
- 前端只能在当前页面会话的内存中保存，不得写入 `localStorage`、Cookie 或 URL；页面刷新后需重新登录获取

### 9.3 强制改密事务

`POST /api/v1/auth/password/forced-change` 接收新密码和确认密码，并执行：

1. 验证改密令牌及用户状态。
2. 验证两次输入一致并满足统一密码策略。
3. 使用当前 Hash 验证新密码与初始密码不同。
4. 更新密码 Hash、`mustChangePassword = false`、`passwordChangedAt = now()`。
5. `credentialVersion` 原子递增 1。
6. 写入 `FORCED_PASSWORD_CHANGE` 审计记录。
7. 在同一事务中提交；审计失败则全部回滚。

改密成功后不自动签发普通令牌。前端必须清除改密令牌并返回登录页，用户使用新密码重新登录。

## 10. 密码与登录安全

### 10.1 统一密码策略

初始化、强制改密、离线恢复和后续用户管理必须复用同一密码策略服务：

1. 长度 12 至 128 个字符。
2. 大写字母、小写字母、数字、符号四类中至少满足三类。
3. 不得包含用户名，比较时忽略大小写。
4. 不得包含首尾空白或控制字符。
5. 不得命中版本库内维护并由自动化测试固定的弱密码拒绝清单。
6. 密码只允许存在于进程内必要的短生命周期变量中，不得写入日志、审计、错误、命令历史或环境变量。
7. bcrypt 生产默认 cost 为 12；测试只能通过密码哈希接口注入较低成本，不得降低生产默认值。

### 10.2 令牌与凭证版本

访问令牌、刷新令牌和改密令牌必须包含：

- `tokenType`
- `userId`
- `credentialVersion`

认证中间件和刷新接口必须重新读取用户，并拒绝以下情况：

- 用户不存在或已禁用。
- 当前时间早于 `lockedUntil`。
- 令牌凭证版本与用户当前版本不同。
- 普通业务令牌对应的用户仍要求强制改密。
- 令牌类型与目标接口不匹配。

本 Spec 保留现有普通访问令牌和刷新令牌有效期，不在本次范围内调整全局会话时长。

### 10.3 登录失败与临时锁定

1. 每次密码错误后原子递增 `failedLoginCount`。
2. 连续失败达到 5 次时设置 `lockedUntil = now() + 15 分钟`，并写入 `LOCKED` 登录事件。
3. 有效普通登录成功后清零失败次数和已过期锁定状态。
4. 未到期锁定期间拒绝登录，不延长锁定时间。
5. 用户不存在、密码错误和账号锁定对外统一返回 `AUTHENTICATION_FAILED`，不得泄露账号是否存在。
6. 登录成功、失败和锁定均记录安全事件；日志写入不得包含密码、令牌或原始异常堆栈。
7. 失败计数、锁定状态和登录安全事件在同一事务内更新；登录成功时，登录时间、计数清零和成功事件也在同一事务内更新。
8. 登录状态或安全事件写入失败时不得签发任何令牌；无效凭据仍保持拒绝，不因日志异常降级为放行。

## 11. 离线恢复

离线恢复用于首位超级管理员因忘记密码、持续锁定或全部会话失效而无法登录的场景，不是日常密码重置功能。

### 11.1 前置条件

1. 必须在交互式终端运行。
2. `ALLOW_SUPER_ADMIN_RECOVERY` 必须精确等于 `true`。
3. `SystemInitialization.PRIMARY` 必须存在。
4. 输入的用户名必须与初始化记录指向的用户一致。
5. 目标用户必须仍持有 `SYSTEM_SUPER_ADMIN` 角色；不一致时失败关闭并要求人工调查。
6. 恢复原因去除首尾空白后长度为 10 至 500 个字符。
7. 新临时密码满足统一密码策略且不得与当前密码相同。
8. 确认短语必须精确匹配 `RECOVER <dbName> <username>`。

### 11.2 恢复事务

恢复服务在一个事务内：

1. 更新临时密码 Hash。
2. 设置 `mustChangePassword = true`。
3. 设置 `passwordChangedAt = now()`，记录临时凭据实际被替换的时间；`mustChangePassword` 仍负责标识该密码不可作为长期凭据。
4. 清零 `failedLoginCount` 和 `lockedUntil`。
5. 原子递增 `credentialVersion`，使全部既有令牌失效。
6. 写入 `SUPER_ADMIN_RECOVERY` 审计记录。

恢复成功后，操作人员必须立即移除或关闭 `ALLOW_SUPER_ADMIN_RECOVERY`。CLI 不自动编辑 `.env`，也不尝试重启服务。

### 11.3 恢复禁止事项

恢复命令不得：

- 创建新用户或第二位超级管理员。
- 恢复任意普通用户或系统管理员。
- 变更角色、权限、组织或员工关系。
- 修改或替换 `SystemInitialization`。
- 跳过强制改密。
- 输出新临时密码。

## 12. 审计要求

本 Spec 复用 `OperationLog` 记录高价值安全操作：

| 操作 | `action` | `targetType` | `targetId` |
| --- | --- | --- | --- |
| 首次初始化 | `SYSTEM_BOOTSTRAP` | `SYSTEM_INITIALIZATION` | `PRIMARY` |
| 强制改密 | `FORCED_PASSWORD_CHANGE` | `USER` | 用户 ID |
| 离线恢复 | `SUPER_ADMIN_RECOVERY` | `USER` | 首位超级管理员 ID |

规则：

1. CLI 操作没有已认证应用身份，因此初始化和恢复审计的 `userId = null`；强制改密使用目标用户 ID。
2. 初始化审计只记录初始化版本、根组织 ID、超级管理员 ID、脱敏数据库名和主机名。
3. 恢复审计记录目标用户 ID、恢复原因、主机名和结果。
4. 不记录密码、Hash、令牌、完整数据库 URL、环境变量值或原始异常堆栈。
5. 审计与被审计变更必须处于同一事务；审计失败即业务失败。
6. 应用不提供修改和删除安全审计的接口。
7. 任何未来归档或导出能力不得破坏在线审计记录的完整性。

## 13. CLI 错误处理与退出码

| 退出码 | 含义 | 行为 |
| --- | --- | --- |
| `0` | 成功 | 输出简短成功结果 |
| `2` | 输入、非交互终端或确认失败 | 不写数据，输出可操作提示 |
| `3` | 系统已经初始化 | 不写数据，不视为可重试写入 |
| `4` | 数据库状态不一致 | 失败关闭，要求人工调查 |
| `5` | 数据库连接或 migration 状态错误 | 不写数据，提示先修复环境 |
| `6` | 离线恢复开关未启用 | 不连接后续恢复流程 |
| `70` | 未预期内部错误 | 输出关联 ID，不输出敏感堆栈 |

CLI 不对写操作执行自动重试。数据库瞬时错误、事务冲突或审计失败均以非零退出码结束，由操作人员确认数据库状态后重新运行。

## 14. 测试策略

### 14.1 单元测试

至少覆盖：

1. 根律所名称、用户名、密码、确认短语和恢复原因校验。
2. 密码复杂度、用户名包含、弱密码、首尾空白和旧密码复用。
3. 初始化状态、脏数据库、恢复开关和目标用户规则。
4. 三类令牌的类型、期限和凭证版本校验。
5. 登录失败计数、锁定、过期解锁和成功清零。
6. CLI 输入映射、脱敏输出和退出码；领域规则不得靠 CLI 测试代替。

### 14.2 PostgreSQL 集成测试

必须使用真实 PostgreSQL 16 测试库，不得使用 SQLite 或内存数据库替代：

1. 成功初始化后恰好存在一条根组织、一个系统超级管理员角色、一个用户、一个用户角色、一条初始化记录和一条审计记录。
2. 第二次执行不产生新数据并返回“已经初始化”。
3. 两个并发初始化只有一个成功。
4. 任一创建步骤或审计写入失败时全部回滚。
5. 初始化记录缺失但应用表已有任意数据时失败关闭。
6. migration 未完成、失败或漂移时拒绝初始化。
7. 恢复开关关闭、用户名不匹配、角色不匹配、确认短语错误时均不写数据。
8. 恢复成功后密码更新、强制改密恢复、锁定清除、凭证版本递增且审计存在。

### 14.3 API 与认证测试

1. 初始密码正确时只返回 5 分钟改密令牌。
2. 改密令牌访问业务接口、刷新接口或 `/auth/me` 时被拒绝。
3. 新密码不合规或与初始密码相同时事务不改变。
4. 改密成功后必须重新登录，旧令牌全部失效。
5. 恢复后全部旧访问令牌和刷新令牌失效。
6. 用户禁用、凭证版本变化、令牌类型错误和锁定状态均由服务端拒绝。
7. 连续失败 5 次触发 15 分钟锁定，外部响应不暴露用户是否存在。

### 14.4 前端测试

1. `PASSWORD_CHANGE_REQUIRED` 登录结果只进入强制改密页面，不写入普通认证状态。
2. 强制改密完成前不能进入 OA 主界面或受保护路由。
3. 改密成功后清除临时令牌并返回登录页。
4. 页面不显示数据库信息、令牌、密码、内部异常或调试信息。
5. 初始化和离线恢复功能不出现在页面或菜单中。

## 15. 验收标准

本 Spec 的后续代码实施只有在以下条件全部满足时才算完成：

1. 已完成 migration 的空 PostgreSQL 16 数据库可通过一次 CLI 操作完成初始化。
2. 初始化只创建本 Spec 定义的六类记录，不创建员工、岗位、权限或业务数据。
3. 应用启动、安装、migration、测试和打包均不会隐式初始化。
4. 系统不存在初始化或恢复 HTTP 接口及 Web 设置向导。
5. 初始化成功后再次执行命令被永久拒绝。
6. 并发初始化只有一个事务成功，失败事务无残留数据。
7. 初始密码登录只能进入强制改密流程，完成后必须重新登录。
8. 改密与恢复均递增凭证版本，使旧令牌失效。
9. 连续登录失败按照 5 次、15 分钟规则锁定，且不泄露账号存在性。
10. 离线恢复只能作用于初始化记录中的首位超级管理员，并受环境开关、交互确认和恢复原因保护。
11. 初始化、强制改密和离线恢复均形成不可由应用修改或删除的审计记录。
12. 全部单元测试、真实 PostgreSQL 集成测试、API 测试、前端测试和统一 `npm run verify` 通过。
13. `.env`、密码、令牌、数据库连接串和运行审计产物未进入 Git。
14. 文档明确记录初始化与恢复的操作手册和故障调查路径。

## 16. 发布边界与风险控制

| 风险 | 控制措施 |
| --- | --- |
| 重复或并发初始化 | 固定单例记录、PostgreSQL 事务锁、唯一约束、锁内二次校验 |
| 脏数据库被静默接管 | 全应用表空库检查、失败关闭、无 `--force` |
| 初始密码长期有效 | 首次登录只签发 5 分钟改密令牌、强制改密后重新登录 |
| 凭据重置后旧会话仍有效 | 所有令牌绑定 `credentialVersion` |
| 暴力尝试超级管理员密码 | 5 次失败锁定 15 分钟、统一错误响应、安全事件记录 |
| 恢复命令被日常滥用 | 精确环境开关、仅交互终端、目标固定、原因和确认短语、审计 |
| CLI 泄露凭据 | 隐藏输入、禁止参数和环境变量传密、输出脱敏 |
| 超级管理员绕过治理 | 不赋予数据库权限，不允许删除审计，完整授权和复核留给后续 Spec |

MFA 不属于本 Spec 的实现范围，但它是超级管理员正式生产上线的安全门槛。SPEC-002 可以在本地和受控测试环境验收；在身份认证安全专项 Spec 完成 MFA 并通过验收前，不得把“首位超级管理员可登录”记录为完整生产安全能力已就绪。

## 17. 审核结论项

批准本 Spec 即表示确认：

1. 使用领域服务 + 薄 CLI，而不是 Web 向导、启动初始化或 seed。
2. 初始化只创建根律所和首位超级管理员，不创建虚假员工。
3. `SystemInitialization.PRIMARY` 是永久、不可重置的初始化事实。
4. 首次登录强制改密，所有令牌绑定凭证版本。
5. 离线恢复只面向首位超级管理员，并受显式环境开关与审计约束。
6. 第二位超级管理员、系统管理员治理、完整组织和权限体系由后续独立 Spec 实现。
7. 本 Spec 通过书面审核后，下一步只生成细化到文件、测试与提交节点的实施 Plan，不直接生成代码。
