# SEC-SPEC-001：依赖安全基线与供应链治理设计

> 状态：已批准，进入 Implementation Plan
> 批准日期：2026-07-16
> 日期：2026-07-16
> 适用项目：`LayerManage/law-firm-system`
> 前置基线：SPEC-001、SPEC-002 已完成本地验收，Node.js 固定为 `22.14.0`
> 编号说明：业务路线中的 SPEC-003 已预留给“组织架构与人员主数据”，本安全专项使用 `SEC-SPEC-001`，不占用业务 Spec 编号
> 实施约束：本轮只批准设计。批准后必须单独生成 Implementation Plan，不在本轮升级依赖或修改代码

## 1. 背景

当前项目通过三个独立的 npm 锁文件管理根工程、服务端和前端依赖，并使用 Node.js `22.14.0`、npm `10.9.2` 与 lockfile v3。现有 CI 使用 `npm ci` 和项目测试验证可构建性，但没有生产依赖风险门禁、开发依赖例外治理、SBOM 产物或依赖升级回归规则。

2026-07-16 的 npm 审计快照显示：

| 范围 | Low | Moderate | High | Critical | Total |
| --- | ---: | ---: | ---: | ---: | ---: |
| 服务端完整依赖树 | 2 | 13 | 8 | 0 | 23 |
| 服务端生产依赖 | 0 | 7 | 7 | 0 | 14 |
| 前端完整依赖树 | 1 | 1 | 5 | 0 | 7 |
| 前端生产依赖 | 0 | 0 | 4 | 0 | 4 |

生产高危风险不应成为律师事务所经营 OA 的长期发布基线。与此同时，直接执行 `npm audit fix --force` 可能引入主版本降级、框架插件不兼容、认证行为变化或锁文件大面积漂移，因此必须采用可审计、可回滚、分层验证的治理方式。

## 2. 目标

1. 将服务端和前端生产依赖中的 `critical` 与 `high` 风险降为零。
2. 将完整开发依赖树中的 `critical` 风险降为零；未能立即消除的开发高危风险必须形成有期限的书面例外。
3. 建立结构化、失败关闭的依赖审计工具和 CI 门禁，不依赖人工阅读 npm 文本输出。
4. 建立依赖升级、锁文件更新、兼容验证、回滚与复核流程。
5. 使用 npm 自带能力生成 CycloneDX SBOM，避免为了生成 SBOM 再引入未经治理的工具依赖。
6. 保持 Node `22.14.0`、PostgreSQL 16、三份 lockfile v3 和现有 `npm run verify` 行为边界。
7. 确保安全扫描报告、SBOM、日志与例外记录不包含环境变量值、令牌、密码、数据库连接串或业务数据。

## 3. 非目标

本专项不包含：

1. 操作系统补丁、Docker Desktop、PostgreSQL 镜像或基础设施镜像扫描。
2. SAST、DAST、渗透测试、WAF、主机防护或运行时入侵检测。
3. 业务功能、数据库模型、API 契约或页面交互的功能扩展。
4. 自动执行 `npm audit fix`、`npm audit fix --force` 或自动合并依赖升级 PR。
5. 一次性升级所有框架主版本或借安全修复进行无关重构。
6. GitHub 远端、分支保护或第三方依赖机器人账号的实际开通；仓库配置应为未来接入预留接口。

## 4. 基线与风险分组

### 4.1 服务端生产风险

当前重点链路包括：

| 风险链路 | 当前直接版本/来源 | 处置方向 |
| --- | --- | --- |
| `egg-cors -> @koa/cors` | `egg-cors 2.2.4` | 升级或替换插件，并同步收紧 CORS 配置 |
| `egg-jwt -> koa-jwt2 -> jsonwebtoken/lodash.set` | `egg-jwt 3.1.7` | 优先验证删除未被业务认证链使用的插件，不接受盲目降级 |
| `egg -> urllib -> undici` | `egg 3.34.0` | 先尝试兼容范围内升级，再评估 Egg 主版本兼容性 |
| `form-data`、`qs`、`uuid` 等传递依赖 | 多条框架链路 | 通过上游安全版本更新，不直接覆盖未知兼容边界 |

代码审查显示，认证领域服务直接使用 `jsonwebtoken 9.0.3`，而 `egg-jwt` 仅在 Egg 插件配置和类型声明中启用，未被当前认证实现调用。实施阶段应把“删除未使用的 `egg-jwt` 插件”作为优先候选，而不是采纳 npm 给出的可能导致版本倒退的自动修复建议。

现有 CORS 配置同时使用 `origin: '*'` 与 `credentials: true`。该配置与 CORS 高危链路具有实际相关性，插件升级必须与允许来源白名单、开发环境策略和回归测试一起完成，不能只更新版本号。

### 4.2 前端生产风险

当前高危链路集中在：

| 风险链路 | 当前直接版本 | 处置方向 |
| --- | --- | --- |
| `axios -> form-data` | `axios 1.15.2` | 升级到审计无高危的兼容版本，回归请求拦截器与认证错误处理 |
| `react-router-dom -> react-router` | `react-router-dom 7.14.2` | 升级到安全版本，回归登录、强制改密、受保护路由和导航 |

前端生产依赖修复原则上先于开发工具链，因为它们进入实际浏览器产物和用户交互路径。

### 4.3 开发与打包风险

开发依赖中的主要风险来自 `vite`、`@yao-pkg/pkg`、`egg-bin`、`egg-mock`、Mocha 及其传递依赖。它们不直接进入服务端生产运行依赖或浏览器生产依赖，但会影响本地开发、CI、测试和 Windows 打包环境，因此不能被永久忽略。

开发高危可在满足第 7 节例外规则时短期保留；开发 `critical` 不允许保留。

## 5. 方案决策

### 5.1 采用方案：分层修复、结构化门禁、人工批准升级

治理顺序固定为：

1. 刷新审计快照并确认风险链路和可达性。
2. 修复前端生产高危依赖。
3. 修复服务端可在兼容范围内消除的生产风险。
4. 删除未使用的高风险插件或依赖。
5. 对必须进行的框架/插件破坏性变更执行独立兼容测试。
6. 治理开发与打包依赖，并建立短期例外。
7. 加入 CI 门禁和 SBOM 产物。
8. 以干净安装、全量验证和重新审计完成验收。

所有依赖变更必须由开发者明确修改 `package.json` 与对应 lockfile，并经过代码审查。CI 只负责发现、阻断和报告，不自动修改依赖。

### 5.2 不采用的方案

| 方案 | 不采用原因 |
| --- | --- |
| `npm audit fix --force` 一次性修复 | 可能跨主版本、降级插件、扩大锁文件变化，无法证明认证、CORS、打包和测试行为保持正确 |
| 只生成审计报告、不设门禁 | 风险会持续累积，报告无法形成发布约束 |
| 所有风险一律立即阻断 | 会把开发工具链中的不可达风险与生产风险混为一谈，导致例外转入非正式沟通 |
| 将在线审计加入日常 `npm run verify` | npm registry 不可用会破坏离线开发；在线门禁应由独立 CI job 承担 |
| 依赖机器人自动合并 | 缺少兼容性、人审和业务回归证据，不适合认证与律所经营系统 |

## 6. 安全门禁模型

### 6.1 门禁矩阵

| 依赖范围 | Critical | High | Moderate/Low |
| --- | --- | --- | --- |
| 服务端生产依赖 | 阻断 | 阻断 | 报告并进入治理清单 |
| 前端生产依赖 | 阻断 | 阻断 | 报告并进入治理清单 |
| 服务端开发依赖 | 阻断 | 阻断或有效例外 | 报告 |
| 前端开发依赖 | 阻断 | 阻断或有效例外 | 报告 |

SEC-SPEC-001 首次验收不得依靠生产 `critical/high` 例外通过，生产范围必须真实达到零。未来紧急生产例外不属于本专项首次验收路径，必须单独审批且最长 7 天。

### 6.2 扫描命令边界

实施后根工程应提供清晰命令：

- `security:audit:prod`：分别扫描服务端和前端 `--omit=dev` 结果并执行生产门禁。
- `security:audit:all`：扫描完整依赖树并执行开发依赖门禁与例外校验。
- `security:policy:validate`：离线校验策略和例外文件，不访问 registry。
- `security:sbom`：分别生成服务端和前端 CycloneDX JSON。

在线审计不得加入本地 `npm run verify`。`verify` 只应加入离线、确定性的策略结构检查；CI 使用独立的 dependency-security job 执行在线审计和 SBOM 生成。

### 6.3 失败关闭

以下情况必须返回非零退出码：

1. npm audit 输出缺失、不是合法 JSON 或 schema 不受支持。
2. registry 网络失败、认证失败、限流或命令被异常终止。
3. 任一生产 `critical/high` 风险存在。
4. 任一开发 `critical` 风险存在。
5. 开发高危没有匹配的有效例外，或例外已过期。
6. 策略文件存在未知字段、重复项、通配符或无效日期。
7. 服务端或前端任一工作区没有被扫描。

扫描不可用与“零风险”必须严格区分，禁止把空输出解释为通过。

## 7. 例外治理

开发高危例外必须使用仓库内结构化文件管理，每条记录至少包含：

| 字段 | 规则 |
| --- | --- |
| `id` | 稳定且唯一 |
| `workspace` | 只能是 `server` 或 `web` |
| `package` | 精确包名，不允许通配符 |
| `advisories` | 精确 GHSA 或 npm advisory 标识列表 |
| `scope` | `development`；首次验收不允许生产高危例外 |
| `reason` | 说明不可立即修复原因和可达性判断 |
| `mitigation` | 已采取的限制措施 |
| `owner` | 明确责任角色或团队 |
| `approvedBy` | 与责任人不同的复核角色 |
| `createdAt` | ISO 8601 日期 |
| `expiresAt` | 最长不超过 `createdAt + 30 days` |
| `trackingRef` | 对应实施任务或缺陷编号 |

例外规则：

1. 过期即阻断，不允许自动续期。
2. 新 advisory 不得被旧例外的包名顺带覆盖。
3. 包升级后不再命中 advisory 时必须删除例外。
4. 例外不得降低测试、lint、构建或 SBOM 要求。
5. 原始 npm audit JSON、环境信息和机器路径不进入例外文件。

## 8. CI 与供应链产物

### 8.1 CI job

`.github/workflows/ci.yml` 应新增独立 `dependency-security` job：

1. 固定 Node `22.14.0`。
2. 对根工程、服务端、前端执行 `npm ci`，不运行自动修复。
3. 执行离线策略校验。
4. 执行生产和完整依赖审计。
5. 生成服务端、前端 CycloneDX SBOM。
6. 上传脱敏后的审计摘要和 SBOM artifact。
7. 任一步失败时 job 失败，不影响其他 job 输出诊断，但阻断合并和发布。

### 8.2 SBOM

使用 npm `10.9.2` 自带的 `npm sbom --sbom-format=cyclonedx`，不新增 SBOM 第三方依赖。服务端和前端分别生成，禁止合并成无法识别归属的单一文件。

SBOM 与审计产物：

- CI 中作为有保留期限的 artifact 保存。
- 默认不提交生成文件到 Git。
- 不包含 `.env`、数据库 URL、token、业务数据或本地绝对路径。
- 必须能追溯 commit SHA、Node 版本、npm 版本、workspace 和生成时间。

| 位置 | 预期职责 |

## 10. 测试策略

### 10.1 审计工具测试

至少覆盖：

1. 两个 workspace 均为零风险时通过。
2. 任一生产高危或严重风险时阻断。
3. 开发严重风险即阻断。
4. 开发高危在有效例外下通过，在缺失、错误或过期例外下阻断。
5. 包名相同但 advisory 不同不能错误复用例外。
6. 空输出、截断 JSON、未知 schema、npm 非预期退出和网络失败均失败关闭。
7. 输出只包含包名、severity、advisory、scope 和脱敏摘要。
8. Windows 与 Linux 路径、换行符和 `npm.cmd` 调用均可用。

测试必须使用固定 fixture，不依赖实时 registry，确保本地和 CI 可重复。

### 10.2 依赖升级回归

每一组依赖变更至少执行：

1. 对应 package 的 lint、typecheck 和测试。
2. `npm run verify` 全量验证。
3. PostgreSQL 16 测试库 reset、测试和最终空库断言。
4. 服务端认证、强制改密、会话失效和超级管理员保护回归。
5. CORS 允许来源、拒绝来源、预检、凭据和错误配置回归。
6. 前端登录、强制改密、受保护路由、Axios 拦截器和导航回归。
7. Windows 打包输入与产物安全契约回归。
8. 干净 `npm ci` 后重新审计，证明风险确实消失且 lockfile 无意外漂移。

### 10.3 人工验证

1. 从允许来源访问 API 成功，从未允许来源访问失败。
2. 登录、刷新、强制改密和退出流程不因依赖升级回归。
3. CI 报告和 SBOM 可下载、可解析、无敏感信息。
4. 模拟过期例外时 CI 明确失败并给出安全摘要。

## 11. 验收标准

只有以下条件全部满足，SEC-SPEC-001 才算完成：

1. 服务端生产审计为 `critical=0`、`high=0`。
2. 前端生产审计为 `critical=0`、`high=0`。
3. 服务端和前端完整依赖树均为 `critical=0`。
4. 所有保留的开发高危均有精确、未过期且不超过 30 天的例外。
5. 不存在生产高危或严重例外用于绕过首次验收。
6. `egg-jwt` 已被证明必要并安全升级，或作为未使用插件完整删除。
7. CORS 不再使用 `origin: '*'` 与 `credentials: true` 的组合，并有自动化回归测试。
8. CI dependency-security job 能在零风险时通过，在生产高危、开发严重、过期例外和扫描不可用时失败。
9. 服务端和前端 SBOM 均能生成并作为 CI artifact 保存。
10. 仓库及 CI 中不存在 `npm audit fix --force`、自动依赖修复或自动合并逻辑。
11. 三份 lockfile 保持 lockfile v3，所有依赖安装使用 `npm ci` 验证。
12. Node `22.14.0` 下 `npm run verify`、PostgreSQL 测试与最终空库断言通过。
13. 审计摘要、例外、日志和 SBOM 不含敏感配置或业务数据。
14. 最终报告记录修复前后风险计数、变更依赖、兼容性证据、剩余例外和责任人。

## 12. 风险与控制

| 风险 | 控制措施 |
| --- | --- |
| 自动修复引入破坏性版本 | 禁止 `--force`，显式变更 manifest，分组提交和回归 |
| npm 建议错误降级或跨主版本 | 以代码可达性和上游兼容性为依据，不盲从自动建议 |
| 删除插件破坏 Egg 启动 | 插件配置、类型声明、启动、认证和打包测试一起验证 |
| CORS 升级后误开放来源 | 环境化白名单、失败关闭、预检与凭据测试 |
| 在线审计不稳定 | 独立 CI job，扫描不可用明确失败；离线 fixture 保证工具测试稳定 |
| 例外长期存在 | 最长 30 天、双人复核、过期阻断、不得通配 |
| SBOM 引入新的工具风险 | 使用 npm 内置 `sbom`，不新增生成器依赖 |
| 审计产物泄露信息 | 只输出安全摘要，禁止环境值、绝对路径和原始业务数据 |
| 依赖升级夹带无关改造 | 限制文件边界，按风险链分组提交 |

## 13. 审核结论项

批准本 Spec 即表示确认：

1. 采用 `SEC-SPEC-001`，保留业务 SPEC-003 的原有编号用途。
2. 首次验收必须消除全部生产 `critical/high`，不得用例外绕过。
3. 开发 `critical` 必须为零，开发高危只允许最长 30 天的结构化例外。
4. 采用分层人工升级，不使用 `npm audit fix --force`。
5. 在线审计进入独立 CI job，日常 `npm run verify` 只包含离线策略检查。
6. 使用 npm 内置 CycloneDX SBOM，不新增 SBOM 工具依赖。
7. `egg-jwt` 优先评估删除，CORS 风险必须同时修复依赖和配置。
8. 书面审核通过后，下一步只生成细化到文件、测试和提交节点的 Implementation Plan，不直接修改依赖或代码。
