# OA 多维协作工作区调整建议

日期：2026-09-14。状态：历史方向建议，已由 [SPEC-COLLAB-20260914](../superpowers/specs/2026-09-14-feishu-aligned-collaborative-workspace.md) 及更新后的 MOD-002 接替为开发输入。下文保留初次评估记录；其中把自建表放在 P2 的排期已被新规格替代，自建表现为 P1 必交。本建议及新规格均不代表功能已经实施。

## 1. 判断与产品定位

建议将产品定位调整为“面向律所业务的多维协作工作平台”：员工以数据表、视图、记录和协作为日常入口；案件、合同、财务、审批等领域服务保障业务正确性。

当前差距同时存在于交互方式、可配置数据结构和实时协作能力。保留现有业务底座，增加统一工作区，比全量重写更符合当前项目现状。仅更换侧栏、颜色和表格皮肤不能解决问题。

默认目标是 OA 自主保存业务数据，飞书可作为过渡入口。用户当前并未要求复刻飞书聊天、视频会议、完整文档编辑器或全面迁移线上数据。

## 3. 截图应转化为什么产品能力

截图中的左侧是表和业务资源导航，顶部横向标签表现为视图入口，表头工具区包含字段、筛选、分组、排序等，右上角提供分享和自动化。仅凭截图无法确定每个标签的配置或权限。

飞书官方帮助明确：一个多维表格包含多个数据表，一个数据表可有多个视图；同表不同视图共享记录，筛选、排序等视图配置各自独立。[官方：数据表和视图](https://www.feishu.cn/hc/zh-CN/articles/472603853615-多维表格的数据表和视图)

因此应建立以下概念，而不是为每个人复制一张表：

```text
承业组织
  └─ 工作区：经营协作 / 案件交付 / 综合管理
      └─ 业务应用：线索与客户
          ├─ 线索表
          │   ├─ 全部线索（团队视图）
          │   ├─ 我负责的（负责人＝当前登录员工）
          │   ├─ 今日待跟进（业务时间条件）
          │   └─ 按阶段看板（同一数据源）
          ├─ 跟进记录表（关联线索；一条线索可有多次跟进）
          ├─ 客户表（通过业务转化动作关联）
          └─ 自动化与统计
```

不同名称的表是否应该合并，必须根据实体、主键、基数和历史流程判断，不能只根据截图名称判断。例如跟进记录通常应独立成表；“我负责的线索”应是视图；“签约转化”可能同时涉及线索视图和新建合同业务动作。

## 4. 界面设计

- 全局入口：工作区、我的待办、通知、知识库、智慧办案。组织权限和系统治理收进管理入口。
- 工作区内部：左侧显示业务应用中的表、统计和自动化；不要把全部后台菜单平铺给员工。
- 表格顶部：表名称、个人/团队视图标签；支持复制视图、保存配置、默认视图与收藏。
- 工具栏：新增记录、字段配置、筛选、分组、排序、行高；权限决定可见和可执行动作。
- 中心网格：单元格编辑、键盘移动、范围复制粘贴、冻结列、列顺序、附件预览、成员选择、关联记录。
- 记录详情：右侧抽屉承载完整字段、关联业务、跟进、附件、评论和变更历史，保留复杂业务详情页的深链接。
- 核心业务动作：分配、公海领取、签约、确认收款、审批通过等以明确按钮执行；表格只显示结果或发起对应命令。
- 手机：同一数据与权限模型，优先记录列表、详情和轻量表单，不把桌面宽表强行缩小。

交互优先级应高于像素级模仿。首轮验证员工能否在表内完成高频任务，是否明显减少页面跳转和重复录入；不能保证零学习成本。

## 5. 数据与业务架构

推荐“固定核心业务表 + 动态扩展字段 + 受控自建表”三者共存。

| 数据类别 | 保存方式 | 写入约束 |
|---|---|---|
| 客户、线索、合同、收款、案件等核心对象 | 保留现有 PostgreSQL/Prisma 实体 | 通过领域服务校验权限、状态、事务和审计 |
| 核心对象新增的业务扩展字段 | 独立扩展值记录，以稳定 fieldId 和对象 ID 索引；JSONB 作为首轮候选 | 服务端类型、范围和字段权限校验；高频查询按实测建索引 |
| 新建活动登记、内部台账等轻量表 | 通用 Record + 类型化字段元数据 + 扩展值 | 工作区授权和配额；禁止悄悄成为合同/财务第二套事实来源 |

核心对象通过 BusinessTableAdapter 暴露给统一表格引擎，查询和变更均委托原领域服务。初期不复制核心数据到另一套通用记录表，避免双写不一致。

建议新增或细化的对象（名称为提议，不是现有模型）：

| 对象 | 职责 |
|---|---|
| Workspace、Base、WorkspaceMembership | 工作空间、业务应用、成员与管理范围；成员关联现有组织和账号 |
| TableDefinition | 记录数据源类型：核心业务适配器或通用自建表 |
| FieldDefinition | 稳定 ID、类型、显示名、校验、选项、敏感级别；字段改名不破坏引用 |
| ViewDefinition、UserViewPreference | 个人/共享范围、筛选树、排序、分组、列序、列宽、视图类型和配置版本 |
| Record、BusinessRecordExtension | 分别承载自建表记录、核心记录扩展值；避免重复核心字段 |
| RecordRelation | 稳定跨表关系、基数、删除策略和目标访问检查 |
| RecordComment、RecordRevision | 记录讨论、提及、变更轨迹；敏感历史按权限返回 |
| AutomationRule、AutomationRun | 规则、执行身份、输入版本、执行结果、失败与重放 |

所有对象都应明确组织隔离和工作区归属；记录字段值不能绕过其数据源的业务边界。附件复用可用的现有文件能力，不直接把可永久公开访问的 URL 存为权限依据。

多维处理分层交付：先类型字段、筛选排序分组和关联记录，再查找引用、聚合与受控公式。公式使用受限表达式和函数白名单，补齐依赖图、循环检测、重新计算、空值/错误语义及计算预算；不允许任意 JavaScript/SQL。公式和关联汇总不能泄露无权读取的字段或记录。通用表格底座不等于完整 Excel 兼容。

## 6. 多人协作与权限

多人可以登录不同账号，不等于多人实时协作。建议第一版采用服务端权威保存、细粒度 PATCH、乐观并发检查和增量通知。

1. 客户端提交 tableId、recordId、fieldId、newValue、expectedVersion、mutationId。
2. 服务端重新校验组织、数据范围、字段权限和业务状态，以版本条件更新；核心动作转领域命令。
3. 首版使用记录级版本：两人改同记录时，后提交者可能收到冲突。界面展示最新值与本地输入，允许复核重试；不得静默覆盖。
4. 单元格级版本或无冲突字段合并作为后续优化。对有跨字段约束的更新保留记录级事务边界，不能无条件合并。
5. 数据与可靠事件在同事务提交，通过现有事件中心衔接推送层；SSE 或 WebSocket 的选型在会话认证与部署约束验证后确定。
6. 推送按权限过滤，优先发送失效通知并重新授权拉取数据。补齐断线重连、事件游标、去重、权限撤销和缓存清理。
7. 显示“保存中/已保存/失败/冲突”，断网保留当前未提交输入并明确状态；首版不承诺离线自动合并。
8. 评论、@提醒、附件和历史绑定记录 ID。在线成员提示可后置，不能替代并发正确性。

表格结构化编辑首版不必直接引入 CRDT；复杂文档多人同段编辑另立范围。

权限取交集：现有角色与数据范围 ∩ 工作区授权 ∩ 字段权限 ∩ 业务动作约束。分享不能绕过原权限。

“我负责的”是筛选条件，不是安全边界。接口、导出、统计、关联查找、搜索和实时事件都必须执行实际权限校验。飞书也提供让仪表盘统计跟随访问者权限的机制，可作为本系统设计参考。[官方：仪表盘权限统计](https://www.feishu.cn/hc/zh-CN/articles/181520041196-仪表盘数据支持跟随访问者权限统计)

## 7. 配置权应如何调整

现有 MOD-002 将配置集中在系统管理员并纳入治理审核。建议新增分层，作为需求变更明确记录，而不是直接忽略旧规则：

- 员工：保存个人筛选、排序、列布局；普通浏览偏好不进入组织级发布审批。
- 被授权的业务负责人：维护团队共享视图、低风险扩展字段和轻量表模板，操作留痕；发布权限由工作区角色控制。
- 系统管理员：核心字段映射、领域适配器、跨业务规则和资源配置。
- 治理审核：核心业务状态、权限扩大、敏感字段、已有字段类型迁移、破坏性结构修改沿用相应高风险控制。

个人视图不能把敏感字段公开，共享视图修改应有版本和恢复方式。字段删除采用归档，历史值可按权限追溯；类型变更需迁移及兼容检查。

自动化复用事件中心，采用“触发→条件→动作”的受限模型；执行时校验规则身份的当前权限，配置修改有版本，执行有幂等键、失败记录、重试次数和循环保护。先实现提醒、任务创建等小闭环，再开放业务状态变更。已有事件模型不等于已有业务人员可用的规则编辑器。

## 8. 飞书关系与迁移策略

| 路径 | 适用目标 | 主要取舍 |
|---|---|---|
| 飞书继续承载日常协作，OA 提供专用业务能力 | 近期最优先保持现有工作方式 | 仍依赖飞书的数据模型、授权和接口能力 |
| OA 自建多维协作工作区 | 需要自主数据和长期产品控制 | 需承担表格、协作、权限和迁移的持续建设 |
| 过渡期对接飞书，按业务域逐步切换 | 希望逐步转向自主平台 | 需要明确每阶段唯一写入端与冲突处理 |

本建议以第二条为目标，可结合第三条推进。若“员工完全继续在飞书工作”优先级最高，应先重新评估第一条，无需先开发完整平台。

用户提供的开放平台首页及多维表格 API 概述是集成文档入口，不能据此认定飞书整套前端可直接嵌入或其引擎可私有化部署。本次页面为动态渲染，正文未完整取得，不据此承诺具体 API、额度、授权或兼容性。[多维表格 API 概述入口](https://open.feishu.cn/document/server-docs/docs/bitable-v1/bitable-overview)

迁移按以下顺序执行，当前不操作任何线上飞书数据：

1. 盘点实际 Base/表/视图、稳定 ID、字段类型、关联关系、公式、自动化和权限。截图只作界面参考。
2. 选择一个团队、一条业务链，确认哪些是实体、哪些是视图，确定该阶段唯一写入端。
3. 建立 sourceSystem/baseId/tableId/recordId 与 OA ID 映射；外部成员映射到现有账号/员工，不仅凭姓名。
4. 在测试环境迁移样本，校验记录数、关联完整性、金额/日期/时区、枚举、空值、附件可访问性与权限差异。
5. 迁移数据与重建视图/公式/自动化/权限分别验收，不能把导入 CSV 当作完整迁移。
6. 影子只读核对后短暂冻结该业务域写入，补齐增量并核对；切换后旧入口只读。禁止长期双端无规则写入。
7. 回退保留映射和导出快照，并有切换后新增记录的回补方案，不能只恢复旧数据库备份而丢掉新数据。

## 9. 建议实施顺序与验收

不按未经验证的人天估算承诺日期；先通过试点确定网格、查询和并发成本。

| 阶段 | 交付 | 通过条件 |
|---|---|---|
| P0 方向与模型 | 高频任务清单、表/视图映射、配置权分层、试点原型；登记需求差异 | 业务负责人用真实流程确认能覆盖其日常操作；不涉及线上数据迁移 |
| P1 线索协作闭环 | 工作区外壳、线索/跟进数据适配、个人/共享表格视图、基础动态字段、行内编辑、详情抽屉、基础关联、权限及并发防覆盖、增量刷新 | 两账号协作更新可见；冲突可复核；切换视图不复制数据；换设备保留视图；无权字段在网络响应中也不可见 |
| P2 多维处理与组织协作 | 看板/日历/表单、批量粘贴、查找聚合、受控公式、评论提及、提醒自动化、业务负责人自建轻量表 | 同源多视图一致；批量失败明确；公式循环可定位；自动化重放不重复执行；权限撤销及时生效 |
| P3 核心业务扩展及迁移 | 案件、合同、财务适配，飞书迁移工具和核对报表 | 网格操作遵循原业务规则；导入幂等、关联和附件核对通过；切换及回退演练完成 |

P1 首选线索→跟进试点，因为现有模型、页面和权限已有基础。合同财务涉及强状态约束，放在通用编辑和领域适配边界验证之后。

P1 还需在约定环境下选定真实峰值规模测试：记录量、字段数、复杂筛选、在线人数、附件量及权限分布。服务端分页/筛选/排序/分组，网格虚拟化，避免把所有数据下载到浏览器。具体性能指标由试点规模确定，并记录查询与保存延迟、冲突率和重连恢复时间。

## 10. 工程落点

- 前端新增 `features/workspaces`、`features/table-engine`、`features/collaboration` 等独立模块；路由可采用 `/workspaces/:workspaceId/bases/:baseId/tables/:tableId/views/:viewId`。
- 将现有线索页面的字段显示规则整理为注册元数据，但核心业务字段编辑仍逐个确认能力，不能自动将所有列变为可写。
- 通用引擎支持 FieldRenderer、CellEditor、ViewRenderer 与 DataSourceAdapter；批量粘贴、虚拟滚动等需求通过小型原型验证后再决定沿用 AntD 或引入专业网格，避免未验证就换技术栈。
- 后端新增元数据、视图和协作服务；沿用现有认证、领域事务、授权、事件与审计。通用查询只接受受控字段及操作符，不接受任意 SQL。
- 将 MOD-002 从后台配置扩展为含业务自助配置的需求；同步评估 MOD-001、MOD-004/005、MOD-013 及权限、事件、一致性、非功能契约。
- 经方向确认后再编写可执行工程规格与追溯项。本文件是评估建议，不把任何新能力标记为已实现或已验收。
