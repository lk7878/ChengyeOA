# PostgreSQL 迁移方案

## 1. 目标与范围

将 LayerManage 当前 SQLite 数据迁移至 PostgreSQL，保持业务编号、关联关系、账号、权限和历史记录一致，为后续 Prisma 开发建立唯一数据库基线。

## 2. 迁移原则

1. 先迁结构和字典，再迁主数据和业务数据。
2. 迁移脚本可重复执行，使用业务唯一键和 upsert 保证幂等。
3. SQLite 原库全程只读保留，迁移失败不影响原数据。
4. 迁移完成后经过数量、约束、关联和业务抽样验证才允许切换。

## 3. 类型映射

| SQLite | PostgreSQL | 处理规则 |
|---|---|---|
| INTEGER 主键 | uuid | 生成 UUID，并保存旧 ID 映射 |
| INTEGER 布尔 | boolean | 0/1 转 false/true |
| REAL 金额 | numeric(18,2) | 按两位小数转换并核对合计 |
| TEXT 时间 | timestamptz | 明确原时区后转换为 UTC |
| TEXT JSON | jsonb | 解析校验失败的数据进入异常清单 |
| TEXT 枚举 | varchar + 字典 | 使用稳定英文编码 |

## 4. 迁移顺序

1. 备份 SQLite、上传文件和环境配置。
2. 建立 PostgreSQL 数据库、角色、扩展和连接参数。
3. 执行 Prisma baseline migration 创建空结构。
4. 迁移组织、岗位、员工、用户、角色、权限和字典。
5. 迁移渠道、线索、客户和联系人。
6. 迁移合同、应收、收款、案件、任务和沟通记录。
7. 迁移审批、通知、绩效和操作日志。
8. 重建外键、唯一约束和索引。
9. 执行数据验证和业务抽样。
10. 冻结 SQLite 写入，执行最终增量迁移并切换连接。

## 5. ID 映射

建立临时表 `migration_id_map(entity_type, old_id, new_id)`。所有外键迁移先查映射；迁移结束后保留只读归档，便于追查历史引用。

## 6. 验证清单

| 类型 | 验证内容 |
|---|---|
| 数量 | 各表源记录数、成功数、跳过数、异常数 |
| 关联 | 无孤立客户、合同、收款、案件和任务 |
| 唯一性 | 用户名、业务编号、外部流水号无重复 |
| 金额 | 合同金额、应收、实收、退款合计一致 |
| 状态 | 状态编码可映射且符合新状态机 |
| 权限 | 用户登录、菜单、数据范围和字段脱敏正确 |
| 文件 | 文件元数据与物理文件存在且 Hash 一致 |

## 7. 切换与回滚

- 切换前进入维护窗口，停止业务写入并记录切换点。
- 保留 SQLite 只读副本和 PostgreSQL 切换前快照。
- 若出现核心链路失败、金额不一致或大量关联缺失，立即停止新库写入并切回 SQLite。
- PostgreSQL 已产生的新数据不得丢弃，应导出为回滚差异清单后处理。

## 8. 环境配置

- `DATABASE_URL` 只通过环境变量配置，不提交真实账号密码。
- 开发、测试、预发布、生产使用独立数据库和最小权限账号。
- 生产启用 TLS、连接池、慢查询日志、每日全量备份和 WAL 持续归档。
- 设计目标：核心数据库 RPO 不超过 1 小时、RTO 不超过 4 小时。
