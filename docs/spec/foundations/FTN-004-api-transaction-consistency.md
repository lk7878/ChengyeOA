# FTN-004 API、事务与一致性

## 1. 契约概述

源 PRD §12 API、事务与一致性。本契约定义承业 OA 系统需求侧的 API 规范、事务边界与一致性策略，作为所有业务模块「接口」「事务」「事件」相关段的统一引用源。本契约的 API/事务要求散落实现在各 SPEC（SPEC-001, SPEC-003, SPEC-004 等）。

## 2. 契约定义

源 PRD §12.1 API 规范 + §12.2 事务边界 + §12.3 一致性策略。

**§12.1 API 规范：**

1. 所有接口统一返回 `{ code, message, data, requestId }`。
2. 列表接口必须支持分页、排序、筛选、关键词和数据范围过滤。
3. 新增和状态流转接口必须校验幂等，关键接口使用 `idempotencyKey`。
4. 错误码按认证、权限、参数、业务规则、外部服务、系统异常分类。
5. 每个接口必须标注权限资源、数据范围、审计动作和事务边界。

API 类型：

| 类型 | 用途 | 示例 |
|---|---|---|
| 资源 API | 创建、查询、更新业务对象 | 创建线索、查询合同、更新案件任务 |
| 状态流转 API | 触发受控状态变化 | 合同生效、收款确认、案件结案 |
| 事件 API | 查询事件、重试投递、人工处理失败事件 | 查看 `contract.formal_signed` 的投递记录 |
| 回调 API | 处理用户即时交互 | 审批同意、AI 结果确认、任务完成 |
| 文件 API | 上传、下载、预览、归档文件 | 上传录音、下载刑事材料 |

资源 API 设计要求：

1. 资源 URL 应围绕对象命名，例如 `/api/contracts/{id}`、`/api/leads/{id}/events`。
2. 状态变化不使用通用 update 直接改状态，应使用明确动作接口，例如 `/api/contracts/{id}/activate`。
3. 所有写接口成功后，必须按业务规则写入 EventLog。
4. 批量写入接口必须明确“全部成功或全部失败”，避免部分成功导致业务链路不可解释。
5. 回调 API 必须快速返回用户可理解的处理结果，复杂处理转异步事件。

**§12.2 事务边界：**

| 业务动作 | 事务要求 |
|---|---|
| 线索转客户 | 客户去重/创建、线索状态、负责人、跟进记录同事务 |
| 首签合同生效 | 合同状态、应收计划、材料任务、分析委托同事务 |
| 正式委托合同生效 | 合同状态、应收计划、案件建档、风险告知同事务 |
| 收款确认 | Payment、PaymentPlan、Contract 收款状态同事务；统计可异步 |
| 客户合并 | 客户、联系人、线索、合同、案件关联迁移同事务并审计 |
| 低满意度触发 | 满意度状态、专项分析流程、通知同事务 |
| 业务事件产生 | 业务对象变更与 EventLog 写入同事务 |
| 审批任务处理 | ApprovalTask、ApprovalInstance 状态和审批事件同事务 |
| 同步回调处理 | 回调操作记录、业务状态变更和事件写入同事务 |
| 配置发布 | 配置版本、发布记录、审核结果和配置事件同事务 |
| 数据干预 | 干预申请、审核结果、业务变更、前后快照和审计日志同事务 |

**§12.3 一致性策略：**

1. 合同、收款、客户、案件主链路必须强一致。
2. 经营驾驶舱允许最终一致。
3. AI 转写和提取采用异步任务，失败后可重试，不阻塞合同签约主流程。
4. 外部 API 调用失败必须保存失败原因、重试次数和人工处理入口。
5. EventLog 必须与业务写入保持事务一致，EventDelivery 可以最终一致。
6. 重复事件、重复回调、重复消息必须通过 `event_id`、`idempotencyKey` 或业务唯一键去重。

### 多维协作一致性扩展（2026-09-14，待实现）

[SPEC-COLLAB-20260914](../../superpowers/specs/2026-09-14-feishu-aligned-collaborative-workspace.md) §7/8 为记录、结构和视图配置的并发与接口契约。普通字段按最小变化提交；记录版本、结构版本和视图配置版本分别校验。P1 记录级乐观锁，同记录不同字段也可能冲突；服务端拒绝旧版本，客户端保留输入并提示复核，禁止静默覆盖。

建表与默认视图同事务；值、版本、审计和可靠事件同事务。批量单请求全成功或全失败，明确上限；大规模导入是独立任务，不暗称跨批次原子。结果未知时复用原幂等键，同键异内容拒绝。查询、计数和分组必须先授权，资源 ID 相互校验归属。

配置归档/迁移执行引用检查，旧结构编辑器不能写入新结构。视图配置保存与记录自动保存有独立反馈。断线重连、重复/乱序消息和过期游标恢复不得回退数据；不得用客户端推送代替事务成功。

验收对应 AC-01/04/06/08/11/12/13/16，核心签约/收款事务规则保持不变。

## 3. 规则与边界

4. 错误码按认证、权限、参数、业务规则、外部服务、系统异常分类。
5. 每个接口必须标注权限资源、数据范围、审计动作和事务边界。

事务边界规则：每个业务动作的关联实体写入须在同一数据库事务内完成，相关审计与事件同步写入。具体业务动作的事务要求见 §2 事务边界表。

## 5. 验收要求

源 PRD §14.1 通用验收要求中与本契约相关的条目：

1. 接口验收：参数校验、权限校验、数据范围、分页、错误码、审计记录。
2. 事务验收：合同生效、收款确认、客户合并、低满意度触发必须验证一致性。
3. 事件验收：事件生成、订阅、投递、失败重试、幂等消费、人工处理必须可验证。
4. 回调验收：审批同意、任务完成、AI 结果确认等同步回调必须校验权限、状态和重复提交。

PRD §14.2 端到端验收链路中与本契约相关：

- 上述链路的关键状态变化均能在 EventLog 中查询到事件，在 EventDelivery 中查询到投递结果。
- 重复提交合同生效、重复确认收款、重复处理审批任务时，系统应通过幂等机制避免重复生成应收、案件、通知或统计。
- 系统管理员发起合同/收款/案件状态干预后，系统在超级管理员审核通过前不得修改业务数据；通过后保留前后快照和完整审计链路。

### U5-A 业务来源一致性

正式三类来源核心字段拒绝通用网格写入；扩展保存继续工作区→正式行锁序、核心/扩展联合版本、幂等与同事务事件/审计。原客户、谈案、合同动作调用原领域服务，未给原接口虚构统一幂等或实时事件保证；离开详情回到表格回源读取最新正式状态。合同详情异步读取以请求代次丢弃旧路由响应。详见[U5–U7 契约](../../superpowers/specs/2026-09-15-u5-u7-business-unification.md)。

原业务动作的多人可见性复用既有 collaboration.events：选中非 CUSTOM 表时每 5 秒发 business.refresh 失效通知，接收端重新按自身授权读取；消息不携带业务字段。直接协作扩展事件保持原机制。该边界是有界回源刷新，不等同于为全部旧领域命令新增即时 outbox 事件。

### U5-B 案件事务（2026-09-15）

状态受理/办理/归档使用案件锁、乐观版本与 CASE_STATUS 审计；结案及任务/沟通/材料变更递增父案件版本。子对象写入在父锁内重查范围和终态，任务状态在锁内复核，禁止并发重复推进。身份补录使用同一锁及版本，CASE_IDENTITY_REPAIR 记录前后归属和理由，不改既有非空事实。文件删除先事务提交再清理存储，失败不提前删除磁盘数据。[详细契约](../../superpowers/specs/2026-09-15-u5-u7-business-unification.md)。

### U6-A 财务创建重试（实施中）

四种财务创建通过 createOnce 持久化请求结果；同一 actor/key 的事务 advisory lock 先于合同等行锁。同 key 同规范化内容返回原目标，同 key 不同操作/内容 409；每次重放重新执行当前动作和范围授权。正式记录、请求标记、outbox 和审计同事务回滚；无 key 旧调用保留原语义。确认/冲销/开票/退款执行保留原状态与资金锁，退款审批保留原 MFA/Step-Up 的目标版本绑定。新增窗口不使用通用网格写入金额与状态。[事务契约](../../superpowers/specs/2026-09-15-u5-u7-business-unification.md)。
